# 澄清与执行示例

这些示例用于判断缺口类型，不是应用专属规则、必填问卷或固定工具脚本。

| 用户请求与已有事实 | 合适的下一步 | 避免 |
| --- | --- | --- |
| “发微信说我到了”，对话里没有收件人 | 先问发给谁；没有真实候选时自由输入 | 打开微信一路走到发送前才发现没收件人；猜最近联系人 |
| “给张三发微信说我到了” | 查找张三，能够唯一识别则在授权内执行；出现无法区分的同名候选才问 | 再问是否允许发送、是否批准计划；预先索要全部联系人属性 |
| “给当前聊天的人发我到了” | 先观察当前聊天确认对象；对象明确则执行 | 不看页面就问收件人；把别的会话历史页面当当前页面 |
| “打开计算器” | 按工具能力查询入口并启动，核验已打开 | 强制写任务记录、列长计划或先问使用目的 |
| “把这个列表按销量找前三个” | 观察当前列表、排序与结果，记录实际候选 | 让用户描述按钮位置或代读列表 |
| “按上次确认的口味点同款”，记忆存在同一商品明确偏好 | 沿用适用偏好，调查实际可售项，按当前任务授权推进 | 重问整套口味；把以前只查询的任务当付款授权 |
| “给张三订餐”，未确认用餐日期和送达地址，已有其他条件足够 | 一次询问这些决定履约结果的必要缺口 | 固定询问所有预算、人数、菜系字段；把平台默认地址当用户明确选择 |
| 先前“默认那个”只回答应用分身选择，现在进入饮品页面 | 可沿用分身选择；饮品选择按当前请求与其适用偏好判断 | 把这句话扩展成默认口味、收件人或付款方式 |
| 已指定商品，调查后发现缺货或同名选项 | 根据新事实评估替代品是否在已有授权范围；需要选择时再问 | 一开始预问所有缺货情景；擅自扩大替代范围 |
| 用户取消收件人问题 | 记录没有答案；按新指示处理独立部分或说明缺收件人 | 使用默认答案发送；立即弹出相同问题 |
| 已派发发送，随后截图失败 | 先重新观察发送结果，必要时报告不确定 | 再点一次发送，把第一次当未执行 |
| 中途出现登录页 | 先理解当前状态及可用操作，必要时问缺少的用户信息 | 在工具层固定认定必须接管；记录密码到 task_state |
| 用户将“给张三”改为“改发李四”，尚未发送 | 更新原任务的目标对象，重新观察再继续 | 新建独立任务丢掉正文；继续向旧对象发送 |
| 用户改口时消息已发送给原对象 | 如实报告已派发及核验结果，依据新指示判断后续操作 | 声称已经撤回；自动重发或自动删除原消息 |
| 会话恢复时任务记录还是 active | 把记录当上下文，在用户要求继续后重新观察 | 恢复界面就重播上次点击或自行续跑 |

## 记录粒度

结果步骤可以是“确定收件人 → 查找联系人 → 发送并核验”，而不是“点击 (120, 300) → 点击 (500, 720)”。明确对象后的步骤可随页面事实调整。

`constraints` 保留来源；用户明确说“只查询、不下单”是 `user`，已知同一商品的口味是 `preference`，认为页面可能提供筛选是 `assumption`。工具返回事实写入 `facts`。收到答案后移除相应 `unknowns`，不反复把已回答的问题带到下一轮。
