# 新消息与队列暂停：调研、修复与验收

2026-09-28。

## 行业依据

- [Cursor 官方 Agent 文档](https://cursor.com/docs/agent/overview)：执行中可以排队，也可以在下一次工具调用处补充当前任务。两者具有不同的交付时机。
- Pi 本项目锁定 0.87.0，核对 `node_modules/@earendil-works/pi-coding-agent/README.md` 的 Message Queue 和 `docs/rpc.md`：区分 steering、follow-up、abort；终端中 abort 会把未执行消息还给编辑器。BBUI 继续复用 Pi RPC 与 Agent 循环，不照搬终端编辑器，也不再增加调度框架。
- [Anthropic Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)：使用简单、可组合的模式，让模型决定业务步骤。它没有规定“新消息解除暂停”的具体产品规则，下面是结合 BBUI 手机互斥与不重放约束的设计。

## 根因与规则

旧实现把关闭执行环境、锁屏或 STOP 留下的暂停原因一直保留；新消息只加入队列，不区分当前是否还存在需要保护的旧工作。正常资源释放后的迟到故障回调还可能再次写入环境异常。

本轮只在明确提交新消息时处理空闲遗留暂停：

1. 没有原队列、执行项、待继续任务、待回答问题或人工控制时，合法的新提交可以解除旧自动暂停。白名单是 stop、environment、lock、error、restart、shizuku；显式 user 暂停及未知原因仍保留。
2. 原有队列或中断任务不会被新提交顺带恢复；进程重启不会自动重放。当前手机中已经等待的真实任务不会被本轮验收执行。
3. Shizuku 与模型校验先通过，提交先持久化；写盘期间新到的停止或暂停优先，写盘失败不能放行任务。重复提交不能成为解除暂停的动作。
4. 关闭空闲环境只释放资源；有受保护工作或人工控制时继续执行原停止规则。设备回调绑定连接代次，正常关闭后的旧回调不能污染新环境。

## 验收范围

- JVM：自动暂停、显式暂停、旧队列、待继续任务、问题、人工控制、重复提交与停止竞态；正常关闭、重连迟到事件、无虚拟屏时真实系统连接故障。
- 真机：通过真实 MainActivity/WebView 桥接发送到本地模拟模型，验证无需“继续队列”即可启动新的空闲任务；验证暂停保护与提交去重。
- 真机夹具隔离会话控制器，保留用户选中会话、队列、续接信息、草稿及模型配置。安装前后核验原始会话、记忆与加密配置摘要。
- 不请求真实模型或搜索 API，不执行用户当前排队中的真实任务。

## 实现与审查结果

- 子代理分别实现提交/持久化策略、连接故障归属、真机隔离夹具，交叉审查后由主代理复核并安装。
- `ConversationStore` 以控制编号和暂停修订号判断一次新提交能否解除历史自动暂停；同一个原因再次 STOP 也会使旧决定失效。
- `SessionController` 先保存提交，再保存暂停释放。第二阶段失败时保留已经保存的等待项并明确告知仍在暂停，不错误返回“未发送”。
- `SessionPersistenceQueue` 按上次写入成功/失败处理完后的状态生成下一份快照，避免并发保存把失败提交写回。尚未保存的提交不会混入其他快照；关闭时追加最终快照。
- `DeviceUnavailable` 携带连接代次及系统/视频来源；关闭、重新绑定使旧回调失效，无虚拟屏的真实系统故障仍能报告。
- 主代理修正会话管理命令失败后缺少调度检查的分支，避免标题更新失败留下没有暂停原因的等待项。关闭环境确认文案同步为空闲释放行为。
