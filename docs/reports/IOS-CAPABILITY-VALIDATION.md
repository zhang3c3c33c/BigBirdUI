# iOS 无辅助 App 路线实机验证

日期：2026-09-29。范围：技术验证，未接入 BBUI 产品，不代表完成 iOS 全功能适配。

## 结论

在当前 iPhone14,6、iOS 18.6.2（22G100）上，Windows 通过苹果开发者服务可以完成“观察画面 → 触摸操作 → 中文输入 → 再观察”的核心闭环，无需安装 BBUI、WDA 或其他辅助 App。本轮使用手机已有的 MultiTouch Visualizer 验证触点；该应用不是控制通道依赖，设置和主屏也通过同一通道操作。

实际路线：pymobiledevice3 9.34.0 + CoreDevice userspace tunnel + UniversalHID，截图使用 DVT，实时预览使用 BigBirdTouch 随附的 UxPlay 接收器与 PyAV 18.0.0。需要手机信任电脑、开启开发者模式，以及挂载匹配的开发者镜像。开发者镜像不是安装到手机上的辅助 App。本次仅覆盖这一台设备和系统版本。

## 性能

- 连续 10.0008 秒触摸运动期间，PC 收到并解码 **599 帧，约 59.9 FPS**，分辨率 750×1334。静态画面可能主动降低帧率。
- 同期发送 600 个触摸报告，发送调用平均 0.527 ms、P95 0.649 ms。这只是调用写入耗时，不是触摸到画面反馈的端到端延迟。
- 共享已建立连接的 10 次截图耗时 38.75–63.21 ms，平均约 43.28 ms；首次截图及其他测试阶段可能更慢。
- 尚未测量端到端操作延迟、长时间抖动、丢帧恢复、音频与 DRM 内容；不能从 59.9 FPS 推出这些项目已通过。

## 适配时需要解决的问题

1. 当前 DDI 的 Device Hub 媒体授权被拒绝时，BBT 针对明确错误回退 direct UniversalHID；这条路径在本机有效。实时预览仍采用独立 AirPlay，不能宣称苹果原生开发者视频服务已通过。
2. 部分 CoreDevice 服务连接只成功处理一次请求，第二次出现 IncompleteReadError。剪贴板每次 RPC 新建连接后通过；旋转第二次调用遇到相同问题。生产适配应按实际服务生命周期实现，不能无条件重发不确定输入。
3. 原始 CoreDevice AppService 的列表参数与 DDI 不匹配，DVT ApplicationListing / ProcessControl 可用。复用成熟库时仍须固定、测试版本。
4. 当前全局 construct-typing 0.8.0 与 AFC 导入不兼容。本轮只在测试目录安装 0.7.0 后通过，没有修改全局环境。正式包应独立锁定 Python 依赖。
5. 关闭时出现过 Windows asyncio 连接重置/管道终结日志，但测试进程最终退出，后续重连成功。产品退出路径还需做错误归类和回归。
6. BBUI 设备锁、STOP、人工接管、代次、动作去重、坐标校验和不确定派发处理尚未接入这套验证脚本，不能把原型测试当成产品安全契约已验收。

建议第一阶段能力集为主屏截图、实时预览、触摸操作、文本/剪贴板、应用启动与 Home/最近应用。界面按实际能力显示，隐藏 Android 专属虚拟屏和没有 iOS 实现的系统工具。搜索、记忆、会话和队列继续复用现有公共模块。

## 补充：单 USB 视频与控制验证（2026-09-29）

用户选择本次只做 USB，并要求验证同一根 USB 线同时承载实时画面与控制。结论为**未验证通过**，不能将此前 AirPlay 的 59.9 FPS 归为 USB 成绩。

- 重新建立 USB CoreDevice 隧道后，DisplayService 返回 `supportedFeatures: 0`；视频启动被当前设备/DDI 组合以 CoreDevice 9021 拒绝，说明为 `Remote control requires iOS 27.0 or later on this device.` 这不证明所有开发者镜像组合均无法工作，但当前组合确实未产生视频流。见 `runs/ios-validation/usb-media-result.json`。
- 下载官方 iPhoneMirror v1.8.3 免安装包，SHA256 与发布方清单一致：`97c5ded39a9437069cb24fd4ee59fe9775c1ebcf2700e3fd6305c9e424396bf0`。仅解压至忽略的测试目录，调用原生库的只读精确设备预检；API 18 初始化成功，`im_is_libusb0_device_available` 返回不可用。没有启动其 GUI、无线接收器或安装器。
- 当前 iPhone USB 父设备仍使用 Apple 驱动和 `usbccgp`，具有 `AppleLowerFilter`；没有该采集路线要求的 libusb0 过滤驱动。**用户明确选择不修改驱动、停止验证，因此没有安装驱动，也没有启动原生 USB 采集。** 同时采集和控制的兼容性、原生 USB 帧率与延迟均未测得。
- IosScreenCaptureTool 的 `CaptureFrameAsync` 实际反复调用 DVT screenshot；其宣传的帧率上限不是本机连续视频流实测依据。
- 停止后卸载本轮重新挂载的开发者镜像，确认测试进程退出。下载的测试包和源码阅读副本仅保存在 `runs/ios-validation/`，没有接入产品或改动系统驱动。

在当前“保持现有驱动”的约束下，已确认可用的是 USB 控制和单次截图；连续截图的持续预览性能尚未验收，不能承诺与 AirPlay 一样流畅。本阶段不得把全 USB 实时视频标为可交付能力。

## 补充：连续 USB 截图性能（2026-09-29）

随后按用户要求测试连续截图预览，不安装驱动、不启用 AirPlay，仅使用同一个 USB userspace tunnel。复用已建立的 DVT 截图连接，串行请求；预览处理与现有桌面一致：保持原始坐标尺寸、缩放至 900×1200 范围、JPEG quality 78、Base64 与 JSON 封装。测试 Python 为 3.14，尚未接入 Electron 或发布版 Python 3.12。

| 场景 | 持续时间 | 完成帧数 | 平均帧率 | 帧间隔 P95 |
| --- | --- | --- | --- | --- |
| 设置页，只获取原始 PNG | 12.03 秒 | 284 | 23.60 FPS | 44.53 ms |
| 设置页，完整预览编码 | 15.07 秒 | 226 | 15.00 FPS | 72.85 ms |
| 测试应用持续触摸，完整预览编码 | 20.04 秒 | 332 | 16.57 FPS | 66.15 ms |
| 同上，限速 15 FPS | 20.04 秒 | 297 | 14.82 FPS | 71.71 ms |

动态测试显示真实移动触点；无限速阶段 332 帧包含 323 个不同图片哈希，限速阶段 297 帧包含 291 个不同哈希。每个动态阶段发送 1202 个触摸报告；限速阶段写入平均 0.46 ms、P95 0.60 ms，仅是写入耗时，不能视为输入到显示的端到端延迟。JPEG 处理约 19–20 ms/帧。该路径 CPU 开销不低，限速动态阶段约消耗 13.42 CPU 秒/20.04 秒墙钟时间，不代表长期功耗或手机发热已验收。

结论：本机短测下，**单 USB 连续截图加控制可行，适合以约 15 FPS 为预览目标**；已经验证了采集、编码与触摸并行，不等于 Electron 最终显示帧率验收，也不是原生视频流。正式接入仍需测 IPC、页面解码和绘制、复杂动态内容及持续稳定性。预览折叠或页面隐藏时应停止取帧，保持只取最新帧，不积压旧画面。

证据：`runs/ios-validation/screenshot_fps.py`、`screenshot-fps-result.json`、`fps-motion-preview-last.png`。测试结束释放触点、清理测试应用画迹、返回主屏、退出测试进程，并卸载本轮开发者镜像；未改驱动。
