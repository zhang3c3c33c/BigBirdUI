## 结论

在 vivo V2366GA、Android 16 / API 36、Shizuku shell UID 2000、项目内置 scrcpy 4.1 上，标准 EditText 可以通过 scrcpy 的定向粘贴输入中文和 Emoji。主屏切到设置，或主屏编辑器持有输入法连接时，虚拟屏无需重新点击即可继续粘贴；主屏文字未被修改，之后仍能输入。

这证明 BBUI 当时“全局输入法必须属于虚拟屏”的统一检查对这条粘贴路径过强。首次实验仅测试这一事实；后续生产更新见上节。

## 实验方法

首次实验版本的 `ScrcpyPasteIsolationTest` 使用真实 `ShizukuPhoneDevice` 建立 scrcpy 虚拟屏，仅在 instrumentation 中反射调用 `ControlChannel.paste()`，跳过当时的 `awaitInputFocus()`，保留测试屏编号、应用/Activity 和编辑器焦点检查。测试没有调用模型，也没有在真实业务应用中输入、搜索或提交。

传输为设置剪贴板、等待 ACK、读回校验、向 scrcpy 控制通道发送 KEYCODE_PASTE；scrcpy 服务端使用虚拟屏 displayId 注入。输入是否成功由 debug 测试页的 TextWatcher 读回确认，不能只以发送成功或剪贴板 ACK 判断。

主屏通过专用测试页请求输入焦点，使用系统按键输入并提交候选词。微信输入法会暂存按键字符，并将下划线转换成中文标点；准备代码因此改用无标点字符串并按 Enter 提交。未改变用户默认输入法。

## 最终结果

最终测试创建 display 78，instrumentation `OK (1 test)`，包含以下四组真实读回断言：

| 场景 | 粘贴前全局 IME 显示屏 | 虚拟屏结果 | 主屏结果 |
|---|---:|---|---|
| 虚拟屏输入框获得焦点 | 78 | `虚拟屏甲🙂` 精确插入一次 | 未发生文字变化 |
| 主屏切到系统设置，不重点击虚拟屏 | 0 | `设置乙🚀` 精确插入一次 | 未发生文字变化 |
| 主屏输入框已有 `MAINBEFORE` 且持有输入法，不重点击虚拟屏 | 0 | `主屏输入丙中文` 精确插入一次 | 仍为 `MAINBEFORE` |
| 主屏继续输入 `AFTER` 后，再点击虚拟屏输入框 | 0 | `重新聚焦丁` 在新光标位置精确插入一次 | 仍为 `MAINBEFOREAFTER` |

第三项的粘贴前后，IME 客户端均属于 display 0。没有通过抢回全局输入法焦点达成输入。最后一项点击改变了光标位置，因此验证“原文中精确插入一次”，另行记录是否追加在末尾；粘贴本身不保证末尾追加。

原始状态和系统输入法诊断：`runs/paste-isolation/final-results.json`（忽略跟踪）。对应截图同目录。设备模块 16 项单元测试通过，构建通过。
