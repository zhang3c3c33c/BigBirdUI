# BBUI 工具职责审查

日期：2026-09-26。本文件保留改造前的审查证据；后续实现见 `docs/contracts/TOOL-CONTRACT.md`，验证结果见 `docs/reports/TOOL-RESULTS.md`。用户已逐项明确批准密码类型、像素变化及启动中间页的策略调整。

## 设计基准

工具接受明确参数，执行能力范围内的操作，返回事实与证据。模型结合用户目标、既有偏好和当前画面决定下一步；任务是否需要询问用户不由一个底层工具决定。

工具必须准确说明“没有派发”“已经派发”“派发情况不确定”，不能把派发、观察、业务成功混成一个成功/失败。工具也不能自行重复不确定的输入。保留用户 STOP、设备归属、显示屏/坐标身份、动作去重和明确用户配置；这些保证指令按原意执行。

## 审查范围

- 安卓当前入口：`pi/android/bootstrap.mjs` 关闭 Pi 内置工具，仅注册 `pi/android/extension.ts` 的 `phone_action`。沿 HTTP → `AppCoordinator` → `ShizukuPhoneDevice` → Binder/scrcpy 执行。
- 桌面当前入口：`pi/launch.mjs` 选择 `phone_action`，经 `pi/bridge.ts` → `bbui/unified_mcp.py` → `ScreenRegistry` / `UnifiedPhone` 执行。
- 共用 `PhoneSchema` 声明 19 个操作；安卓实际支持列表有 18 个，不含系统面板，其中创建屏幕的语义并未真正实现。
- 旧入口：`bbui/mcp_server.py` 的 `phone_observe`、`phone_act`、`phone_stop`、`phone_resume`，以及 `bbui/cli.py`。当前安卓不使用它们，但它们仍是仓库可调用接口。
- 同时检查工具提示词、桥接错误、原生停止逻辑和聊天工具卡片。没有发起模型联网请求，也没有重放手机动作；本轮未做新的真机行为测试。

## 逐项盘点

| 操作 | 当前问题 | 建议 |
| --- | --- | --- |
| 查看 | 安卓必须先通过前台包名解析；采集时 Activity 变化直接失败；桥接 broken 后所有调用被拒绝 | 观察与输入资格分开。视频仍可读时返回画面及元数据缺失/变化事实；不能生成可执行观察凭据时明确标记，而非装作画面不存在。只读采集可有限重试 |
| 等待 | `时间` 与必填 `执行后等待毫秒` 累加；安卓只读等待不响应任务取消 | 只保留清晰的总等待含义，默认不额外叠加。支持取消等待，结束后返回新画面；等待多久由模型选择 |
| 点击、双击、长按 | 身份、坐标检查之外，用固定像素差阈值判定目标变化；拒绝时只返回错误，没有新图 | 保留坐标/屏幕身份校验。将局部像素变化作为观察证据交给模型，不把动画、光标闪烁等变化等同于必须中断任务。因旧图拒绝时返回新观察，模型重新决策 |
| 滑动、拖拽 | 原语本身基本符合；共享异常路径会使后置观察错误停止整轮 | 保留手势与释放触点的实现；返回实际派发阶段。不要用工具判断是否“翻到底”“找到目标” |
| 放大、缩小 | 原语本身基本符合；时长、坐标、指距有协议约束 | 保留合法参数与多点触控实现，返回图；缩放是否达到目标由模型判断 |
| 输入内容 | 混合了输入焦点归属检查、固定 2000 字限制与“密码框不得输入”业务政策 | 焦点属于正确屏幕/用户是技术条件，应保留。编辑器类型作为事实返回；密码等任务授权与产品政策移到独立策略/Agent 层。长度限制声明为可配置能力，不能静默截断 |
| 删除内容、全选 | 分别发送删除键与 Ctrl+A；没有证明文本已删或已选 | 如实返回按键派发，效果看截图。不要默认成功修改文本；明确作用于当前焦点，与输入工具共享必要的焦点事实 |
| 按键 | Android 与桌面的键集合不同；共用 schema 没有准确列出；最近任务在桌面虚拟屏被禁止、安卓却暴露 | 按后端公开实际支持键与作用域。对全局键不能假称只影响虚拟屏，也不能从桌面限制推断安卓实际路由；需真机验证 |
| 打开应用 | 安卓要求 5 秒内目标包名在前台，否则抛异常并使连接失效；正常选择页无法继续 | 一次启动 + 有界观察，返回系统启动结果、实际前台和截图；目标未到前台是一项事实，不是通道故障。分身/登录/权限等页面由模型处理，不先造厂商决策树 |
| 列出应用 | 安卓只返回当前用户的 launcher 包和单个组件；同包多个入口被去重，关键词/系统应用筛选参数被忽略；无名称和实例信息 | 返回已取得的应用名、包名、启动入口、用户/实例信息与覆盖范围；未知明确标记。不能声称完整枚举分身。不支持的筛选参数不能静默忽略 |
| 系统面板 | 安卓 schema 暴露但执行器拒绝；桌面只允许 main | 当前安卓工具定义不宣称支持；未来若提供全局操作，明确作用域，不偷偷降级到主屏 |
| 创建屏幕 | 安卓实际只是截图并说 virtual 已存在；桌面把创建屏幕与启动 App 绑定 | 安卓从模型操作枚举移除虚假的创建能力，或实现真实、明确的创建/确保存在语义。桌面将分配屏幕和启动应用解耦，便于模型决定任务安排 |
| 列出屏幕 | 安卓返回最后一次启动成功时保存的 `boundPackage`，不保证是当前前台；没有关闭状态表达 | 区分会话标识、显示屏编号、最后启动目标、当前实际前台和连接状态；只返回确认过的事实 |
| 关闭屏幕 | 安卓释放所有通道；下次创建也会先被 ensureConnected 拦住，因此模型没有成对的恢复能力 | 生命周期由宿主管理则不要向模型暴露一个不可恢复的单向关闭；若暴露就提供完整创建/查询/关闭生命周期，禁止隐式重放输入 |

参数必填校验只负责可执行性。`意图` 继续作为展示信息，不改变动作、权限或去重身份；不应因缺少一句展示文案就强制停止。

## 最优先问题：失败被过度升级

### A. 正常启动结果使整个连接失效

证据：`DeviceService.kt:116-142` 对目标前台做 5 秒判断并抛异常；`ShizukuPhoneDevice.kt:393-407` 的 RPC 包装把所有 Throwable 都送入 `binding.fail`。业务异常、命令拒绝、Binder 故障没有区分。

改法：命令结果用数据返回；仅真正的 Binder/传输故障、不可收敛的超时才使相关通道失效。不要对分身选择器加“允许继续”特例，而应让任意可观察的中间页面自然返回。

### B. 动作完成后的观察失败，被改写成动作结果未知

证据：`ShizukuPhoneDevice.kt:215-239` 将派发、等待、截图放在同一个 try 中，任一异常均停止并写“结果未知”。这会覆盖已经记录的“已派发”。

改法：分别记录输入派发状态和观察状态。输入已发出、截图失败，必须仍然返回“已派发；观察失败”。允许只读重新观察；不要因此自动再次点击或输入。

### C. 一次故障封死观察与恢复

证据：`pi/android/bridge.ts:31,57-61` 与 `pi/bridge.ts:26,68-72` 使用全局 broken 状态阻止全部调用；文案要求重新观察，实际又不允许观察。安卓 RPC 包装和执行器还有另一层 stopped / binding failure。

改法：区分用户主动停止、待确认的在途操作、控制通道故障、视频通道故障。观察通道可用则保留；不可用则返回具体事实。技术恢复由宿主协调，不让模型并发抢救通道；恢复代次隔离迟到结果，确认旧输入已结束后才能接收新的输入。禁止后台重试旧动作。

注意：Binder 超时不证明原调用已结束，`DeadlineCall.kt` 已明确厂商实现可能不响应线程中断。不能通过简单清除 broken/stopped 来假装恢复，也不能自动清除用户 STOP。

### D. 桌面端关闭范围过大

证据：`bbui/unified.py:242-245` 任意派发异常都调用 `self.close()`。虚拟屏路径在 `bbui/screens.py` 把 `tool.control` 设为 display，因此 close 可能关闭整个虚拟屏，随后获取错误现场也失败。

改法：先区分业务结果和损坏的通道，仅释放真正需要释放的资源，尽可能保留画面与现场。

## 策略应放在哪一层

### 从工具实现移走的任务级决策

- `pi/android/extension.ts:32`、`pi/phone-extension.ts:34-36`：超过 100 次工具调用就 abort，并要求用户继续；查看、查询也被计数。改成宿主可配置的运行预算，预算策略与工具语义分离；可提前向模型提供剩余预算和重复无进展证据，不在工具里凭固定次数宣告任务必须交给人。
- `pi/android/extension.ts:12`：发送消息、购物、支付、密码、验证码的统一处理政策写在工具扩展提示词里。它们属于任务授权和 Agent 产品策略，应按用户已授权范围和必要约束处理，避免无条件“购物停在下单前”“一律人工接管”。移动策略不意味着自动增加授权。
- `InputFocus.kt:50` 与桌面 `runtime.py` / `unified.py` 的密码输入禁令：不是坐标或通道能力判断。把输入类型作为事实，策略集中管理，不混进焦点解析器。敏感内容仍不应进入展示意图、普通日志或非必要持久化。
- 桌面 `screens.py:271` 的一屏一 App 限制：创建时分配关系成了禁止跨应用任务的规则。移除业务绑定，保留真实任务迁移冲突和设备资源归属检查。
- 桌面最多 3 个虚拟屏、动作时长、输入长度等上限：归类为公开的资源/能力限制，允许配置，不伪装为“用户必须决策”。

### 保留的执行准确性约束

- 用户 STOP 和人工接管优先；模型不能清除用户的停止意图。
- 同一屏幕顺序派发，避免两个动作竞争焦点；输入归属正确的显示屏和用户。
- 坐标范围、屏幕代次、旋转、最新观察编号和动作去重。旧截图导致本次未执行，应尽量返回新证据供模型继续，不等于任务结束。
- 不将不确定派发自动重放；去重记录应返回已有派发事实，不能只说“重复未执行”却丢掉原动作结果。
- 明确由用户配置的禁止范围需要尊重。桌面有 `blocked_packages` 实现；本次检查的安卓执行路径未发现对应配置/执行校验，只有提示词声称存在。需要如实声明，不据此默认增加黑名单或放宽用户已经设置的范围。
- 不支持的能力、权限缺失和协议无效应准确返回。工具少限制，不代表编造支持能力。

## 统一结果契约建议

保留 `phone_action` 外层接口与中文字段，不新增第二套 Agent 循环。各操作按后端能力生成 schema，避免给安卓暴露桌面能力。内部动作仍复用 Pi、Shizuku、scrcpy。

每次调用独立表达：

```json
{
  "动作编号": "...",
  "执行": {
    "状态": "已派发",
    "说明": "已提交一次应用启动请求"
  },
  "观察": {
    "状态": "已取得",
    "截图编号": "...",
    "显示屏编号": 58,
    "前台包名": "com.vivo.doubleinstance",
    "前台Activity": "...",
    "目标应用在前台": false
  },
  "通道": {
    "控制": "可用",
    "视频": "可用"
  }
}
```

执行状态至少区分未派发、已派发、部分派发、未知；观察单独区分取得、失败、未请求。手势中途取消、删除多次中断等只返回实际能确认的进度，不虚构系统已接收或业务效果。

可选识别提示应附依据或标明推断，不要求每个页面都有特定状态枚举。不要增加“必须人工确认”“允许后续动作列表”之类由页面分类推导出的工具决策。可返回设备支持的操作清单，它描述能力，不决定业务路线。

用户停止/接管作为独立宿主状态；具体操作的参数无效、旧截图、本次未执行不应改变它。错误最好包含阶段和机器可读原因，供模型修正参数或重新观察，不只给一句“已停止，请用户继续”。

查询类工具不必填无意义等待，也不必都依赖当前画面；坐标类操作继续要求有效观察。打开应用需要有效的屏幕归属，但不必因当前页面像素变化而拒绝启动。

## 界面状态也需要同步

`ChatStore.kt:217-223` 与 `android/chat-ui/src/main.tsx:46-53` 当前主要按工具是否报错显示完成/失败。改造后调用正常返回仍可能是“未派发”或“已派发但观察失败”，卡片必须展示对应事实。

展示可采用“已发送点击”“已取得画面”“需要重新观察”等描述；任务完成与否由模型结合证据表达。“意图”标题只是模型本步目标，不能拿来证明成功。

## 旧 MCP 接口

- `phone_observe`：节点与截图均依赖同一次观察流程，节点失败不宜让可用截图完全消失；返回各自状态与时间，保留非原子采集事实。
- `phone_act`：包含 launch/tap/tap_point/type_text/input_focused/back/swipe。沿用相同派发/观察契约；`visual_reason` 是解释信息，不应因解释缺失而拒绝一个坐标与观察均有效的操作。`required_texts` 若由模型显式提供，属于调用者主动声明的前置条件，可以保留。
- `type_text` 会替换节点文字，`input_focused` 会粘贴到当前光标，不能在统一时混淆两者。
- `phone_stop` 保留停止能力。`phone_resume` 当前可直接删除 STOP 文件，未验证停止来源；不应让模型绕过用户 STOP。恢复授权由宿主/用户控制，不靠文案承诺。
- 当前安卓不使用这套接口，避免将它们误算为当前手机故障原因。若继续维护，应复用统一执行契约，避免三套策略分叉。

## 建议实施顺序与验收

1. 先拆分结果契约、异常类型和停止来源；修复启动、中间页返回、动作后截图失败以及观察恢复路径。
2. 校正后端 schema、查询信息与工具卡片，处理安卓虚假创建/单向关闭能力。
3. 移走工具内任务策略与固定调用次数决策，软化像素启发式；保留用户配置与技术约束。
4. 桌面与旧 MCP 同步契约，逐步收敛重复实现，不新造执行引擎。

回归重点：分身选择后继续；正常启动/慢启动/启动命令拒绝；已点击但截图失败；旧图拒绝后取得新图；动态按钮像素变化；输入焦点切换与密码类型事实；查询筛选与多入口；重复动作编号；用户 STOP；在途超时和迟到结果；跨屏误投；关闭/重新创建生命周期；工具卡片不把未派发或未知显示成成功。

验收原则：一次可恢复的工具结果不强迫用户接管；模型取得足够证据后自行决定下一步；工具从不虚报结果、自动重放输入或绕过用户停止。
